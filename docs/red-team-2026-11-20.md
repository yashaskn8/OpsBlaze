# OpsBlaze adversarial red-team review — 20 November 2026

## Scope and evidence

**Authorized, non-destructive scope:** code review and adversarial test
campaigns against the isolated OpsBlaze simulator, synthetic signed identity
tokens, local SQLite and native disposable PostgreSQL/Temporal CI. No attack
was performed against a third-party service, real production account,
external network target, or live infrastructure. All changes went directly
to `main`, without Docker, branches or pull requests.

This review targeted authorization, tenant isolation, short-lived credentials,
post-revocation access, approval substitution, persisted-effect status,
unknown-outcome recovery, reservation fencing, replay/deduplication,
cohort-preview information leaks, and evaluation oracle integrity.

## Code-level findings addressed

| ID | Severity if extended to a real adapter | Finding | Defensive fix and regression |
|---|---|---|---|
| RT-01 | High | An impossible positive status response for a PREPARED receipt could repeatedly retry an invalid state transition; incorrect version jumps lacked explicit quarantine. | Fail closed to NEEDS_REVIEW on inconsistent status/version; tests in `test_simulator_effects.py` |
| RT-02 | High | Effect dispatch did not explicitly compare every plan/grant/receipt field, leaving a substitution risk if a trusted component or database record were inconsistent. | Check plan digest, action, tenant/incident, target, version, adapter, grant decision, and version at SENT; tests in `test_plans.py` |
| RT-03 | High | Simulator apply checked a permit against the current target version but did not verify its version was the one frozen in the reservation. | Reject modified permit versions; required E8 `permit-version-binding` scenario and targeted test |
| RT-04 | Medium–High | Revoking the incident creator was not independently checked before subsequent approval and effect dispatch. | Creator and incident target are revalidated at approval/effect evidence gate; tests in `test_plans.py` |
| RT-05 | Medium | A production identity with both operator and reviewer capabilities could reach the reviewer boundary. | Enforce independent reviewer-only authority; align React controls; OIDC negative test |
| RT-06 | Medium | Established SSE sessions did not recheck the persisted identity deny-list after token revocation. | Bind stream to principal and check revocation at each poll; SSE regression |
| RT-07 | Medium | Large event cursors could reach database integer binding or unbounded header parsing. | Bound signed 64-bit cursor range and limit Last-Event-ID to ASCII digits; HTTP regressions |
| RT-08 | Medium | Shadow-cohort preview accepted an arbitrary incident UUID without confirming tenant ownership/existence. | Require tenant-owned incident; tenant-isolation regression |
| RT-09 | Medium | A valid RS256 JWT with multiple audiences or an excessive lifetime could authenticate to the API. | Require one exact audience and no more than one-hour token lifetime; OIDC negative tests |
| RT-10 | Medium | Offline E5 reporting tolerated too few negative-control cases or malformed metadata, weakening an offline safety signal. | Minimum control fraction and count, strict metadata types, immutable report trial digest; tests in `test_heldout.py` |

## New repeatable attack simulations

- Contradictory remote receipt status, forged observed version, premature
  confirmation and target witness inconsistency; no duplicate effect apply.
- Invalid target/adapter/action/plan-digest/expected-version substitutions at
  the SEND authorization boundary.
- Revoked incident creator after approval, before approval, revoked reviewer
  on an existing stream, and dual-role reviewer rejection.
- Wrong-tenant cohort previews, forged or oversized SSE cursors, altered
  held-out oracle metadata and tampered paired trial inputs.
- PostgreSQL multi-session race delivering the same signed IdP revocation
  event repeatedly: assert one revocation, one event and one approval audit.
- E8 simulator conformance now requires **17 distinct scenarios** including
  forged permits, lost replies, provider status retention gaps, and stale
  fences. These simulate provider faults; they do not attest a real adapter.

The dedicated `security-negative` GitHub Actions job runs tests named
`redteam`; the normal backend test job still executes all unit cases.
PostgreSQL concurrency requires the separate native `postgres-temporal-e2e`
job, so unit CI alone is not enough.

## Residual risks — explicitly NOT cleared

1. **Real identity provider:** real PKCE/callback, signing-key rollover,
   privileged role changes, security-event transport authentication,
   real-user revocation and penetration testing require an authorized IdP.
2. **External adapter:** no third-party mutation adapter is enabled.
   Actual provider fencing, idempotency retention, independent postcondition,
   partial failures and real effects are unverified.
3. **Distributed operations:** worker handoff tests run on one CI host.
   Multi-host fault injection, restore exercises, RPO/RTO and load bounds
   remain unmeasured.
4. **Independent AI quality:** real incident outcome custody and held-out
   model-vs-runbook trials are absent. No model or learned policy is certified.
5. **Policy promotion:** E6 approval and live candidate exposure remain
   blocked pending separate human release authority, signed bundles and
   measured canary rollback.
6. **Deployment defense in depth:** external dependency/SBOM, endpoint
   exposure, secret rotation, full accessibility, supply chain and human
   penetration testing still require independent assessment.

**Release decision:** laboratory protections are stronger, but production
readiness is **BLOCKED**. GitHub Actions success establishes only the test
coverage listed above and is not proof of zero vulnerabilities or permission
to operate on real targets. See `docs/production-acceptance-gates.md`.
