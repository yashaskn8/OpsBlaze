## 1. Context and Problem Statement

Following the initial deployment of Stage 11 (Feature E6: Versioned Policy Canary and Rollback), a comprehensive adversarial security and architectural audit identified critical vulnerabilities and architectural divergence that threatened the safety invariants of the agentic control plane:

1. **Client-Asserted Token Issuance:** The `/v1/auth/token` endpoint accepted arbitrary client-provided identities, tenant IDs, and role lists. Any untrusted caller or LLM could mint high-privilege credentials (such as `release_owner` or `incident_commander`) simply by requesting them.
2. **Hard-Coded Secret Fallbacks:** Configuration files and settings fell back to insecure default signing and authentication secrets in production-like configurations, exposing tokens and signed bundles to forgery.
3. **Legacy Tenant-Header Authorization Bypass:** Several core API modules (`incidents`, `evaluations`, `experience`, `improvements`, `lessons`, `outcomes`, `trace`, `workbench`) permitted unauthenticated access when a `X-Tenant-ID` header was present, bypassing cryptographic bearer token verification.
4. **Spoofable P2 Plan Approvals:** The P2 approval routes accepted client-asserted `reviewer_id` and `reviewer_role` in request payloads rather than deriving them strictly from the cryptographically verified principal token.
5. **Client-Simulated Guardrail Breaches:** The public guardrail endpoint accepted `simulated_invariant_breaches` from the client, allowing callers to falsely trip or manipulate guardrails rather than evaluating genuine server-side telemetry.
6. **Passive Guardrail Telemetry:** Canary guardrails were only evaluated on demand when explicitly requested via an API call, rather than running automatically during incident runtime state transitions.
7. **Missing Consequential Fencing on Rollback:** While routing was updated upon release rollback or emergency kill switch activation, in-flight candidate workflows could still attempt consequential actions if B2 resource reservation and P2 approval dispatch did not actively check release state.
8. **Discontinuous E5 Eligibility Checks:** E5 regression gate eligibility was checked only at release creation time, allowing a candidate whose evaluation was subsequently invalidated to proceed through shadow and canary stages.

Stage 11.1 addresses every vulnerability across ten mandatory verification gates (Gate A through Gate J) to ensure fail-closed security and verifiable assurance before expanding agentic capabilities to Feature E7.

## 2. Architectural Decisions & Remediation Design

### Decision 1: Cryptographic Authentication and Production Secret Hardening (Gate A)
- **Zero Insecure Defaults:** In production environments (`ENVIRONMENT == "production"`), `auth_secret_key` and `policy_signing_secret` must be at least 32 characters in length and cannot match known compromised defaults (`"insecure-dev-auth-secret-key-32-chars-minimum"`, `"opsblaze-dev-policy-signing-secret-hex-safe"`). Startup is aborted immediately if secrets are weak or missing.
- **Server-Derived Credentials:** Client-asserted minting on `/v1/auth/token` is permanently decommissioned, returning HTTP 401 Unauthorized for all requests. A dedicated `/v1/auth/login` endpoint validates caller credentials against a server-authoritative directory (`PRECONFIGURED_USERS`).
- **Algorithm Enforcement:** JWT decoding strictly enforces `algorithms=["HS256"]` and rejects the `none` algorithm or mismatched algorithm headers.
- **Token Revocation:** Tokens include a unique JWT ID (`jti`). A server-side `TokenRevocationStore` records revoked tokens; revoked tokens are immediately rejected across all authenticated routes. A dedicated `/v1/auth/revoke` endpoint enables revocation.

### Decision 2: Elimination of Legacy Tenant-Header Authorization (Gate B)
- **Canonical Dependency:** Introduced `get_authenticated_tenant_id` in `backend/api/auth_deps.py`. It cryptographically validates the Bearer token, checks token revocation, extracts the `Principal`, and verifies that if an `X-Tenant-ID` header is provided, it exactly matches `principal.tenant_id`.
- **Complete Route Hardening:** Replaced legacy unauthenticated tenant dependencies across all endpoints (`incidents.py`, `evaluations.py`, `experience.py`, `improvements.py`, `lessons.py`, `outcomes.py`, `trace.py`, `workbench.py`).
- **P2 Reviewer Derivation:** `backend/api/approvals.py` derives the reviewer identity and role directly from the authenticated `principal.actor_id` and `principal.roles`. Client-provided reviewer assertions in request payloads are ignored. Non-human callers (`actor_kind == 'AGENT'`) are rejected with HTTP 403.

### Decision 3: Formal E6 Release Role Matrix (Gate C)
All release operations enforce the strict `RELEASE_ROLE_MATRIX` defined in `backend/domain/auth.py`:
- `release_create` & `bundle_create`: `PLATFORM_ENGINEER`, `RELEASE_OWNER`.
- `release_approve`: `RELEASE_OWNER`, `INCIDENT_COMMANDER`.
- `promote_shadow`, `promote_canary`, `adjust_canary`, `promote_active`: `RELEASE_OWNER`, `PLATFORM_ENGINEER`.
- `rollback`, `revoke`: `INCIDENT_COMMANDER`, `RELEASE_OWNER`, `PLATFORM_ENGINEER`, `SRE_LEAD`.
- `kill_switch`: `INCIDENT_COMMANDER`, `SRE_LEAD`, `RELEASE_OWNER`.
The API helper `check_release_action_role(principal, action)` is enforced across all 12 release transitions.

### Decision 4: Authentic Telemetry-Driven Guardrail Enforcement (Gate D)
- **Forbidden Simulation:** Removed `simulated_invariant_breaches` from `GuardrailCheckRequest` and configured Pydantic with `extra="forbid"`. Any client payload attempting to simulate breaches is rejected with HTTP 422.
- **Server-Side Telemetry:** Added `record_invariant_breach()` to `ReleaseGuardrailService`, which writes genuine breach records directly into PostgreSQL table `release_event_audit`.
- **Audit-Driven Evaluation:** `evaluate_and_enforce_guardrails()` queries `release_event_audit` for Class 1 zero-tolerance events (unauthorized mutations, negative-control breaches, fence violations) and triggers atomic rollback to `ROLLED_BACK`.

### Decision 5: Automated Runtime Guardrail Invocation (Gate E)
- In `backend/persistence/repositories.py`, `transition_status()` automatically invokes `ReleaseGuardrailService.evaluate_and_enforce_guardrails()` whenever an incident reaches a terminal progression state (`RESOLVED`, `ESCALATED_TO_HUMAN`, `CLOSED`).
- If an incident exhibits invariant breaches or safety threshold violations, the guardrail service executes an immediate atomic rollback in the domain database without requiring external polling.

### Decision 6: Consequential Active Safety & Fencing (Gate F)
- `PolicyRouterService.route_incident()` checks release status and kill switch state before returning routing decisions.
- If a release is in `ROLLED_BACK`, `REVOKED`, or has `kill_switch_active = True`, all candidate routing is blocked and fallback to the pinned incumbent baseline is enforced.
- In `backend/effects/fencing.py` (`ResourceFencingService.acquire_reservation()`) and `backend/approvals/service.py` (`ApprovalService.approve_plan()` and `dispatch_action()`), requests are cross-checked against release status. Consequential mutations from rolled-back or kill-switched releases raise `ApprovalPolicyReleaseForbiddenError` (HTTP 403), halting execution.

### Decision 7: Isolated Non-Blocking Shadow Execution (Gate G)
- In `backend/releases/router_service.py`, `execute_shadow_observation()` executes candidate reasoning in a sandboxed path with `consequential_authority = False`.
- Shadow reasoning telemetry is recorded in `release_event_audit` for offline comparison against incumbent outcomes without emitting effects or acquiring resource locks.

### Decision 8: Continuous E5 Eligibility Rechecks (Gate H)
- `PolicyReleaseService._assert_e5_eligibility()` is executed not only during release creation, but continuously on every promotion transition (`promote_to_shadow`, `promote_to_canary`, `promote_to_active`).
- If the underlying E5 evaluation is revoked or marked ineligible, subsequent promotion is rejected immediately.

### Decision 9: Full Frontend Identity & Control Wiring (Gate I)
- Created `frontend/src/services/authApi.ts` exporting preconfigured identities and bearer token handling.
- Integrated a global principal switcher into `App.tsx` and updated all views (`ApprovalCockpitView`, `ReleaseControlView`, `EvaluationsView`, `WorkbenchView`, `TraceExplorerView`, `ExperienceView`, `FailureAndLessonsView`) to pass `Authorization: Bearer <token>`.
- UI action buttons (approve, rollback, kill switch) dynamically disable when the current principal lacks the required server role.

### Decision 10: Static Quality & CI Workflow Hardening (Gate J)
- Ruff linter: 0 errors across `backend/` and `tests/`.
- Mypy type checker: 0 errors across 96 source files in `backend/`.
- Updated `.github/workflows/ci.yml` with containerized PostgreSQL 17, `astral-sh/setup-uv@v5`, Python 3.12, strict linters, type checks, full test suites, and frontend build.

## 3. Consequences

### Positive
- Zero privilege escalation: Clients and AI agents cannot forge credentials, self-authorize, or mint roles.
- Robust defense-in-depth: Consequential mutations fail closed if a policy release is rolled back or kill-switched.
- Audit fidelity: Guardrail decisions are backed by authentic PostgreSQL audit event telemetry.
- Clean separation of duties: Drafters cannot approve their own releases; non-human agents cannot approve P2 plans.

### Negative / Operational Trade-offs
- Integration tests must authenticate as properly privileged principals according to `RELEASE_ROLE_MATRIX`.
- Developers must supply compliant secrets (>=32 chars) when running in production configuration.


## Corrective addendum — 2026-11-08

The initial Stage 11.1 report overstated the completeness of several guarantees.
The follow-up commit establishes these explicit boundaries:

- The built-in password registry is development/test-only. Login returns 503
  outside those environments until a real identity provider and authoritative
  tenant-membership source are integrated.
- Runtime token revocations are stored in PostgreSQL by JTI and signed expiry.
  The API only permits revocation of the caller's current token.
- The React client validates the nested backend principal response, ships no
  password values, and keeps bearer tokens in memory rather than browser storage.
- Shadow execution and durable retryable guardrail scheduling remain open
  acceptance items. Audit-only shadow metadata is not equivalent to candidate
  reasoning, and best-effort post-commit guardrail checks are not durable jobs.

Stage 11.1 remains unaccepted until these open items and the current CI checks
are resolved with executable evidence.
